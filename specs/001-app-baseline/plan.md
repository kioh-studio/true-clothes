# Implementation Plan: MIEN App — Current State Baseline

**Branch**: `001-app-baseline` | **Date**: 2026-06-06 | **Spec**: specs/001-app-baseline/spec.md

**Input**: Feature specification from `specs/001-app-baseline/spec.md`

## Summary

MIEN has a well-built UI layer and a sophisticated server-side outfit generation
engine, but personalisation is broken end-to-end: user wardrobe items are stored only
in local device storage and never synced to Supabase. The fit engine's Edge Function
reads from an empty database and falls back to pre-seeded demo items — real personalised
outfit generation does not work.

This plan addresses that critical gap, closes remaining stubbed UI features (share,
settings, help & feedback), adds live weather integration to the feed, and establishes
the SQL migration infrastructure the project currently lacks.

**Three categories of work:**

1. **Fix** — Wardrobe sync to Supabase (unblocks end-to-end personalisation) and SQL
   migration files (establishes schema version control)
2. **Complete** — Share outfit, Settings screen, Help & Feedback, feed error recovery UI
3. **Extend** — Live weather API integration via Open-Meteo (no API key required)

## Technical Context

**Language/Version**: TypeScript 5.x (strict mode) · React Native 0.81.5 · React 19

**Primary Dependencies**:
- Expo SDK: Router, ImagePicker, Location, Font, FileSystem
- Zustand 5.0.13 with AsyncStorage persist middleware
- @supabase/supabase-js: auth, database, storage, edge functions
- React Navigation: stack + tab navigators (via Expo Router)

**Storage**:
- Local: AsyncStorage (Zustand persist) — session state, UI toggle state
- Remote DB: Supabase PostgreSQL — profiles, measurements, style profiles, clothing items
- Remote Files: Supabase Storage (`wardrobe-photos` bucket) — clothing item photos

**Testing**: Jest + ts-jest · `src/**/__tests__/`

**Target Platform**: iOS 15+ and Android 12+ via Expo managed workflow

**Project Type**: Mobile app (Expo Router, file-based navigation)

**Performance Goals**:
- Outfit feed scroll: 60 fps
- Edge Function response: < 3 s on warm instance
- App cold start to interactive: < 3 s on mid-range device
- Wardrobe photo upload: < 5 s per photo on 4G

**Constraints**:
- Offline-capable for saved/worn/scheduled/local wardrobe state
- Network required for outfit generation and wardrobe sync
- No API keys committed to source control; `EXPO_PUBLIC_*` env vars only
- Supabase client never imported directly from screens, components, or stores

**Scale/Scope**: Personal-use app. ~50 screens, ~15 k LOC. Wardrobe expected < 200
items per user. Single-region Supabase deployment.

### Three Open Deferred Items (from `docs/expectation/expectation.md`)

The following items from the expectation doc "Open / Deferred Work" section are
still unimplemented and constitute the Phase 7 work plan below:

1. **Schema drift** — `supabase/migrations/20260606000002_clothing_items.sql` uses
   `clothing_items.user_id`, but the live DB uses `wardrobes` + `clothing_items.wardrobe_id`.
   A corrective migration is needed to make `supabase db reset` produce the correct schema.

2. **"Add to Collection" on outfit detail** — currently calls `toggleCollection(outfitId)`
   which tracks outfit IDs in `collectionsAddedSet`. This is inconsistent: collections now
   hold wardrobe items, not outfits. Should be repurposed to a collection picker that adds
   the outfit's individual items to a chosen collection.

3. **Collection management UI** — the `+` (create) icon on `collections/index.tsx` and
   the edit icon on `collections/[id].tsx` are visual-only. The store actions
   (`createCollection`, `updateCollection`, `deleteCollection`, `addItemToCollection`,
   `removeItemFromCollection`) exist but no bottom-sheet UI is wired to them.
