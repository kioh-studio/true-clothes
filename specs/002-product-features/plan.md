# Implementation Plan: MIEN — Product Features Phase

**Branch**: `002-product-features` | **Date**: 2026-06-08
**Spec**: `docs/expectation/expectation.md`
**Extends**: `specs/001-app-baseline/plan.md`

## Summary

Phase 1 (`001-app-baseline`) established wardrobe sync, collections, the outfit feed
skeleton, and basic stub completion. This phase closes every gap between the baseline
and the full product vision described in `docs/expectation/expectation.md`.

Fourteen feature streams, prioritised by user value and dependency order:

1. **Personal Color Detection** — hybrid camera + 2 questions → 4-season → personal palette → fit engine
2. **Extended Measurements** — 15-field set, tooltips, camera pose estimation, body shape
3. **Profile Identity** — editable display name, avatar upload
4. **Server-Side Outfit Persistence** — saved/worn/scheduled on Supabase
5. **Feed Pagination + Dedup + Cooldown** — real batching, exclusion list, worn-cooldown
6. **Formula System** — server-driven catalog, global default, per-feed override
7. **Style Catalog** — server-driven Supabase table
8. **Item Detail + Extended Attributes** — full CRUD page, new fields
9. **Wardrobe Category Expansion** — dress/one-piece, headwear
10. **i18n** — Vietnamese + English from the start
11. **Offline Mode** — read-only offline, server actions queue
12. **AI Item Extraction** — Claude Vision pipeline, credit counting, retry logic
13. **IntentContext Scaffold** — type + Edge Function hook for future AI chat
14. **Monetization** — RevenueCat, free/paid tier enforcement

---

## Technical Context

**Language**: TypeScript 5.x strict mode
**Platform**: iOS + Android via Expo SDK (managed workflow + Expo Dev Client for camera)
**State**: Zustand v5 + AsyncStorage persist
**Backend**: Supabase (Auth, PostgreSQL, Storage, Edge Functions — Deno)
**i18n**: `i18next` + `react-i18next` + `expo-localization`
**IAP**: RevenueCat (`react-native-purchases` + Expo plugin)
**Pose Estimation**: TensorFlow.js MoveNet (Expo Dev Client, `react-native-vision-camera`)
**Personal Color Detection**: On-device pixel sampling + LAB color space math (rear camera + flash, no remote AI, no image upload). Utility: `src/utils/colorLab.ts`. `react-native-vision-camera` torch API.
**AI Extraction**: Supabase Edge Function calling `claude-haiku-4-5` vision API
**Performance**: 60 fps feed, <3 s Edge Function, <3 s cold start, <5 s photo upload

## Constitution Check

**Gate 1 — New screens / components** (Principle I): Every new screen uses `T.*` tokens only.
Personal color screen, measurements expansion, profile edit, item detail, formula picker —
all must pass design-token audit before merge. ✅ Planned.

**Gate 2 — Business logic placement** (Principle II): All new logic in stores or
`src/features/**/use*.ts` hooks. No async/await inline in JSX. ✅ Enforced per-task.

**Gate 3 — Supabase access** (Principle III): New service modules: `profileService.ts`,
`outfitInteractionService.ts`, `usageCreditService.ts`, `stylesCatalogService.ts`,
`formulasCatalogService.ts`, `aiExtractionService.ts`. All DB/Storage calls routed through them.
✅ Planned.

**Gate 4 — Types / units / colors** (Principle IV): New domain types in `src/types/`:
`profile.ts`, `measurements.ts`, `intent.ts`, `outfit.ts`. All measurements in cm/kg.
All colors as named strings. ✅ Planned in data-model.md.

**Gate 5 — Scoring logic duplication** (Principle V): Personal palette boost and body
shape scoring added to BOTH `src/services/fitEngine/colorHarmony.ts` (client) AND
`supabase/functions/generate-outfits/engine/`. ✅ Required per task descriptions.

**Gate 6 — Cross-domain comms via stores** (Principle VI): Personal color result written
to `fitEngineStore`. Profile edit writes to `authStore`. No direct feature-to-feature imports.
✅ Enforced by store architecture.

## Phase Breakdown

### Phase 1 — Infrastructure & Schema (unblocks everything else)

Write all 8 migration files. No app code changes.
Milestone: `supabase db push` succeeds; all new tables and columns visible in dashboard.

### Phase 2 — i18n Foundation (must precede all new UI)

Bootstrap `i18next` + `expo-localization`. Add `useTranslation()` to all **existing** screens.
Add `en.json` + `vi.json` with all existing string keys. New screens added in later phases
are built i18n-first.
Milestone: Language toggle in Settings switches all existing screens between EN and VI.

### Phase 3 — Profile Identity

Extend `profileService.ts` for `display_name` + avatar upload. Build `profile-edit.tsx`
screen. Wire real name into Profile tab header. Add avatar picker reusing wardrobe photo
pattern.
Milestone: User edits name and uploads avatar → persists across app restarts.

### Phase 4 — Extended Measurements + Body Shape

Expand `measurements.tsx` to 15 fields with tooltips. Add body shape classifier.
Add consent note. Camera pose estimation is a sub-phase requiring Expo Dev Client — deliver
manually-filled 15-field form first; camera estimation as Phase 4b.
Milestone: User completes all 15 fields; body shape auto-computes and shows on profile.

### Phase 5 — Personal Color Detection

Build questionnaire screen (`personal-color.tsx`). Implement scoring → season → palette
lookup. Store result in `profiles.color_season + personal_palette`. Wire personal palette
into fit engine (boost matching outfits).
Milestone: User completes quiz → season badge shown on profile → outfit feed reflects palette.

### Phase 6 — Style Catalog + Formula System (server-driven)

Seed `public.styles` and `public.formulas` tables. Build `stylesCatalogService` +
`formulasCatalogService`. Update style quiz to pull from Supabase. Build formula picker
in feed + profile. Wire active formula to Edge Function.
Milestone: Admin adds a new style in dashboard → app picks it up on next launch without release.

### Phase 7 — Item Detail + Extended Attributes

Build `/item/[id].tsx` full detail page with edit. Add `name`, `material`, `pattern`,
`warmth_season`, `primary_color` fields to `add-item.tsx` and `wardrobeService`. Expand
category CHECK to include `dress` and `headwear`.
Milestone: User taps item in wardrobe → sees full detail, can edit any field.

### Phase 8 — Server-Side Outfit Persistence

Build `outfitInteractionService.ts`. Migrate saved/worn/scheduled from AsyncStorage to
Supabase `outfit_interactions`. Update `appStore` actions for toggleSave, toggleWorn,
toggleSchedule to write to Supabase. Build worn-cooldown query for Edge Function.
Milestone: Save outfit on phone → shows as saved on a different device (same account).

### Phase 9 — Feed Pagination + Dedup + Cooldown

Update `fitEngineStore.fetchOutfits()` to batch 10, accumulate `shownOutfitIds`,
send exclusion list to Edge Function. Implement scroll-to-end trigger for next batch.
Wire worn-cooldown exclusion.
Milestone: Scroll through 10 outfits → automatic fetch of 10 more; worn outfits absent for 7 days.

### Phase 10 — AI Item Extraction

Build `extract-garments` Edge Function (Claude Vision). Build multi-step extraction flow
in the app (upload → review → confirm). Implement credit counting via `usage_credits`.
Wire free-tier limit (2 scans/month).
Milestone: Upload outfit photo → items extracted → appear in wardrobe with auto-filled attributes.

### Phase 11 — Offline Mode

Audit all server actions for offline-safe behaviour. Add `NetInfo` guard pattern to
all write operations. Show offline banner. Implement optimistic local state with
"pending sync" indicators.
Milestone: Airplane mode → browse wardrobe + cached feed works; add item shows "waiting for connection".

### Phase 12 — IntentContext Scaffold + Monetization

Define `IntentContext` type + add optional field to Edge Function request body.
Add RevenueCat SDK. Build `usePremium()` hook. Gate AI scans and (future) AI chat
behind entitlement check.
Milestone: Free-tier user hits scan limit → sees upgrade prompt; premium user is ungated.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|--------------------------------------|
| Expo Dev Client required for pose estimation | Camera frame processors need native module | Pure-JS TFLite 3–4× slower; WebView bridge unreliable on Android |
| `outfit_data jsonb` snapshot | Outfits are transient; no server-side outfits table exists | Normalising would require a separate outfits schema not in scope |
| Dual engine sync (client + Edge Function) | Constitution Principle V — must stay in sync | Removing client copy breaks debug tooling and offline feed |
